## Run from source on either platform

- Install Node.js 22 or later for development.
- Run `npm ci`, then `npm start` to open the desktop app. These commands work in Windows PowerShell/Command Prompt and macOS Terminal.
- Run `npm run record` for a clean, borderless **1280 × 720 (16:9)** window for client recordings. Resize it while preserving 16:9; use **Cmd + Q** on Mac or **Alt + F4** on Windows to close it. Record the Thought Bubble Studio window. Every app screen stays within a centered 16:9 frame, with black borders when the display has a different shape.
- Press **Ctrl + Shift + C** (or **Cmd + Shift + C** on Mac) in the live screen to open **Select camera**. Press the shortcut again or **Escape** to hide it; choosing a camera also closes it. The selector closes before capture and while operator settings are open. The refresh button finds newly connected cameras. This selection lasts for the current run; save it in **Operator → Station** to use it on future launches.
- `npm run dev` opens the browser development preview at `http://127.0.0.1:5173/`.
- Add `?demo=1` to the browser preview URL to try the full journey with an illustration. Browser preview does not save participant records or submit print jobs. Use the desktop application at an event.

## Operator access

Hold the Cyber Carnival logo for about 2 seconds, or press **Ctrl + Shift + A** (or **Cmd + Shift + A** on Mac). Set a private 6–12 digit PIN on first use. Operator sessions expire after 30 minutes. Switch English/Arabic with **Ctrl + Shift + L** (or **Cmd + Shift + L** on Mac), or use `?lang=ar` in the browser preview.

The operator panel includes:

- **Phrases:** all 60 supplied English phrases with editable Arabic translations, enable/disable controls, and new phrase entry. At least one phrase must remain enabled.
- **Photo:** landscape or portrait print format. Landscape uses the approved photo-and-logo design; editable English and Arabic titles and acknowledgement wording apply to the optional portrait template. New and upgraded stations default to **6 × 4 landscape**.
- **Station:** a selector for every available camera, **Refresh devices** for newly connected cameras/printers, mirrored capture, printer selection, **Save & print test page**, direct printing, fullscreen, and exit.
- **Records:** saved completions, CSV export, and reprint controls.

Select the camera and **Camera quality**, then **Save changes**. The default is **4K · 30 fps**, requested from the physical Insta360 Link 2C. **1080p · 60 fps** is also available. Cameras that cannot provide the requested mode use their closest supported mode. The physical Link 2C is preferred automatically when it is connected; a saved camera selection takes priority. Its virtual camera does not provide 60 fps. [Insta360 specifications](https://www.insta360.com/product/insta360-link2) and [virtual-camera limitations](https://onlinemanual.insta360.com/link2/en-us/specs/compatibility/camera). Operator settings identify the computer and show the automatically selected GPU or CPU processing mode. Allow camera access in macOS or Windows privacy settings. If device names are hidden, allow access and refresh the device list. Close other applications that have exclusive control of the camera.

## Participant journey

1. Lobby mode detects all visible faces locally. Each person activates after a 2-second hold. If a face turns away, visible body evidence keeps the same temporary track and bubbles active. When both face and body are lost, gaps up to 1.2 seconds retain their bubbles and activation, then the bubbles fade out over 650 ms. Returning during the fade smoothly restores the same thoughts; longer departures reset the timer. Safe anchors and extra layout clearance absorb small head turns and off-center movement. One person can receive up to four thoughts, two people up to three each, and groups of three to eight up to two each. First thoughts take priority over extra thoughts, and crowded scenes reduce extras rather than covering faces. Up to eight people receive bubbles; available space can reduce this further. No thought covers a detected face, another thought or the primary action area. Capture requires a fresh, actually detected face; the visual grace period cannot authorize a photo.
2. Tap **Take your photo**. A large **5, 4, 3, 2, 1** countdown starts immediately, giving the person who touched the screen time to move into the camera view. No form or second capture button is required.
3. Face the camera and hold position. After the countdown, the station automatically takes three photographs. All visible, activated participants keep their own thoughts during capture; there is no single selected-person portrait crop. If the camera loses the group or tracking becomes stale, return to the live view and retry.
4. Select your favourite photo and tap **Print your photo**. Landscape photos show the photo and event logo; portrait certificates use a generic participant label.
5. The app saves the selected JPEG and completion record before submitting silently to the configured physical printer. Unselected photographs are discarded when the session resets.
6. The assistant hands over the print. The final screen resets after 45 seconds of inactivity; the selection screen resets after 2 minutes.

## Printing

The default certificate is an **1800 × 1200 JPEG**, designed for **6 × 4 inch landscape photo printing at an effective 300 dpi**. Load 4 × 6 inch (10 × 15 cm) paper, choose landscape orientation, and set the appropriate paper type, tray and borderless option in the printer driver. The landscape photo area is **1800 × 1000**, filled edge to edge with the camera image using a proportional crop, without stretching or artificial side panels. The optional portrait format remains available; reprinting an older photo follows that saved photo’s orientation.

For the event hardware test, follow **TEST-WINDOWS.txt**, also included in the Windows package. In **Operator → Station**, select the printer and click **Save & print test page**. This saves the current settings and prints a calibration certificate with edge markers and colour swatches, without creating a participant record. Printing runs in a hidden background window without a system print dialog. Configure paper type, tray and borderless settings in the operating system printer preferences, then check a physical sheet. For DNP RX1HS, select the single (6x4) media form; the app uses that driver’s default paper size rather than a generic custom form. On macOS with a HiTi P525, select its native **6 x 4** paper form and **Landscape**. The app matches the driver's 156 × 105 mm media dimensions and fits the entire certificate at **95%**, centered on a navy border to protect the photo and logo from trimming. Adjust **Operator → Station → Print size (%)** between 80% and 100%; lower it if an edge is still clipped, then use **Save & print test page** to check the paper. For uneven side borders, adjust **Horizontal position (mm)** in small steps: positive moves the print right, negative moves it left. Both adjustments also apply when reprinting saved certificates.

Printing is always silent, including on upgraded stations. Choose the event printer explicitly, or use the system default physical printer. With only one physical printer installed, it is selected automatically; PDF, XPS, OneNote and fax destinations are rejected to avoid file dialogs. An unavailable saved printer does not silently switch to another device. A `submitted` status means the operating system accepted the job; it does not verify that paper physically came out. Failed printing leaves the saved photo available for retry, with the detailed error in Operator → Records. Unresponsive jobs time out after 30 seconds; inspect the system queue before retrying to avoid duplicates.

If the DNP queue reports “The selected paper size is not compatible with installed media”, inspect the failed job’s requested media. A saved 6×8 job will still fail after changing the printer default to 6×4; cancel that failed job and submit a new 6×4 calibration. On macOS the DNP driver exposes 6×4 as `300dnp6x4`. A local RX1HS calibration completed as one sheet with that media setting, and the operator confirmed that it printed correctly. Repeat the physical test when moving to another computer or changing media.

## Local storage

Use **Station → Open data folder** to locate the station’s files:

- `photos/<record-id>.jpg`: selected certificate JPEGs.
- `records.json`: participant identifier, language, completion date, photo path and print status.
- `config.json`: phrase library and station settings.
- `operator.json`: salted operator PIN hash.

The data folder lives under the operating system’s per-user application data directory. Data is not cloud-synced by the application and is not encrypted by the app. Use the event computer’s OS account and disk protection and manage retention according to the event’s requirements. No face identities, face templates, audio, or continuous video are saved. Back up the data folder if needed before deleting records manually while the app is closed.

## Detection and performance

The bundled full-range sparse BlazeFace model uses a fast full-view worker and a separate CPU worker for overlapping detail crops. At startup the full-view worker warms and times both CPU and GPU inference on the same camera frame, then selects the faster backend. Unsupported GPUs and lost GPU contexts fall back to CPU automatically. On computers with at least four logical processors, CPU mode adds one more full-view worker, allowing two camera frames to run on separate CPU cores. The current source adds one shared CPU person worker, for three workers when face detection uses GPU and at most four when face detection uses CPU. It uses the bundled EfficientDet Lite0 int8 model at up to eight frames per second with one frame in flight, independently of face processing. Body observations keep their source timestamp and expire from the detector cache after 500 ms; they preserve established visual tracks but never authorize a photograph without a fresh face. There is no model or saved identity per person. Platform and processor architecture are detected by Electron; the same app pipeline runs on Apple Silicon and Windows.

The camera requests 3840 × 2160 at 30 fps by default. Full-view inference receives a 640-pixel-wide copy; the separate recovery worker receives a 1280-pixel-wide copy and scans six overlapping crops at up to 30 crop jobs per second. The live camera and certificate use the original camera frame, without shrinking the saved photograph to detector resolution. Detection is driven by new decoded video frames, separately from the display animation; the old 12 fps cap is removed. Each worker accepts only one frame at a time, excess frames are dropped, and late CPU results cannot rewind tracking. Cached detail detections retain their original observation timestamps and expire after 250 ms. They cannot refresh activation or authorize capture after the 300 ms freshness limit. The two-second participant settle remains intentional.

With the Insta360 Link 2C, **4K supplies at most 30 fresh frames per second**. The interface can animate at 60 fps independently. The optional 1080p mode requests 60 camera frames per second; actual tracking speed also depends on the computer, camera driver, lighting and exposure. A GPU is used only after its measured speed beats CPU; no manual GPU or platform selection is needed.

Run `npm run benchmark:tracking` for a repeatable synthetic 4K/30 check with one, four and eight repeated portrait fixtures. It starts a local preview, uses installed Chrome, records display fps, actual full-view detection fps, inference time, result latency, face retention and bubble counts, then writes `artifacts/tracking-performance.json` and screenshots. Add `-- --cpu --moving` to exercise the real CPU worker pool and a moving eight-person scene, saving a separate `artifacts/tracking-cpu-fallback.json` report. The existing fixture is a development asset, not a live crowd. It must be present at `tests/fixtures/portrait.png`; this benchmark does not download it or contact external services. Use `/qa.html?live=1&paused=1` to check the actual station camera separately. Do not treat synthetic results as a guarantee for a Windows PC or the event's people and lighting.

Live thought bubbles use a separate transparent WebGL2 compositor. Glass skins, labels and icons are uploaded as cached textures; movement, tilt, breathing, opacity and contact deformation are composed on the GPU. The compositor scales to the display’s pixel density, with a 4096-pixel buffer limit. It falls back to the shared 2D renderer if graphics are unavailable or a context is lost, and resumes GPU rendering after context recovery. Photographs and printed certificates keep the same full-quality 2D artwork. Operator settings show face processing and bubble rendering separately. `npm run verify:gpu` checks sprite appearance, texture reuse, graphics loss/recovery and 2D fallback on a GPU-equipped development computer with the preview running.

Public camera status text, face brackets and diagnostics are hidden to keep the installation readable from a distance. Face count, selected CPU/GPU backend, inference time and separate detection/display rates remain available as camera data attributes for development checks. Reduced-motion preferences disable drifting, glass breathing and squash. Each of the four glass variants caches three transparent skins. The skins drift, tilt and breathe independently on slow, different rhythms; reflections follow their skin while text stays steady. Reduced-motion views and photographs use the still composite. Text layers and wrapping are cached, with font-load invalidation. Live view and certificates share the same artwork. Thought anchors follow their owner on every display refresh, with a bounded distance from an expanded head region. Primary thoughts are allocated before optional extras, and all visible heads are protected. Small corrections use damped movement; collision corrections preserve opacity and do not bounce or squash. Tail dots share collision clearance with other dots, rendered bubbles and heads. Photos reuse the current layout at print dimensions. This is a 2D visual simulation. Earlier Blender artwork remains in `assets/bubbles/` for reference.

A local stationary eight-person physics benchmark averaged approximately 0.12 ms per display frame after this change, compared with 2.95 ms before it (600 simulated frames, including initial allocation). This measures JavaScript layout/physics only, not camera inference, drawing, or event hardware performance.

Primary implementation references: [Google web worker guidance](https://developers.google.com/edge/mediapipe/solutions/vision/face_detector/web_js) and [model details and CPU/GPU benchmarks](https://developers.google.com/edge/mediapipe/solutions/vision/face_detector). GPU performance depends on the runtime and hardware; it is not automatically faster.

## Verification

`npm test` checks camera recovery, multi-face matching and independent activation, group capture readiness and loss, worker backpressure and disposal, moving-crowd collision boundaries, reduced motion, resizing, print layouts, authentication and saved records. `npm run build` checks TypeScript and generates the offline application. `node_modules/.bin/electron scripts/verify-print-layout.cjs` renders the current calibration to a one-page 6 × 4 PDF without submitting a printer job.

For a repeatable development camera check, run `npm run dev` and open `/qa.html`. This clearly labelled test page feeds a repeated public portrait fixture through the real bundled detector. It offers one-, two-, three-, four-, six- and eight-person scenes, motion, face loss, a 200 ms detection dropout, a small third-face recovery check and a calibration export. In the small-face check, the full-view pass finds two people while the combined detector/tracker retains all three. Add `?wide=1` to inspect the full landscape camera in a narrow preview panel; `?artwork=1` previews the four animated transparent blue shells and offers still PNG downloads. The test toolbar shows face/bubble counts, frame rate, physics/drawing timings and layout revisions. Open `/qa.html?live=1&paused=1` for a real-camera check with Start/Stop controls, actual detection outlines, full-view versus combined counts, inference/frame timings and text-motion diagnostics. Stopping the check releases the camera; this page does not record video. It is excluded from desktop packages and never activates automatically. It is a synthetic group fixture, not evidence of live crowd accuracy. The real event camera must be checked separately. Run `npm run verify:tracking` for a real-model synthetic test that masks the face while the body moves, restores the face, removes the person, and verifies a new session on re-entry. The QA toolbar also offers **Mask face for body tracking**. This tests sustained missing-face evidence, not physical head-turn accuracy. The kiosk drawing establishes the screen and camera placement, but the camera lens field of view and mounting angle determine the final standing distance. Hardware camera quality and physical paper output must be checked on the event PC and printer.

Additional optional Playwright checks are in `scripts/verify-ui.cjs` and `scripts/verify-desktop.cjs`; they intercept printer submissions rather than sending physical jobs. Run the UI script first to generate its certificate fixtures. Use `PLAYWRIGHT_PATH` to select an alternate installed Playwright package if needed.
